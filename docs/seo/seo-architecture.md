# SEO architecture

SEO here means _being findable and correctly understood_, not volume. The strongest SEO asset
this platform can build is a small set of pages that are visibly better sourced than the
alternatives, on a site whose structure makes its scope legible to a crawler.

Everything below is implemented from typed registries. Nothing is hand-written per page.

---

## 1. Metadata

All page metadata is produced by `src/lib/metadata.ts`. Pages call a builder; no page writes a
`<title>`, canonical, or Open Graph tag by hand. This makes drift impossible and gives us one
place to change the templates.

### Title templates

Defined in the root layout via `metadata.title.template`.

| Page class | Pattern                                             | Example                                  |
| ---------- | --------------------------------------------------- | ---------------------------------------- |
| Home       | `JusticeCenterID — Understanding Justice Worldwide` | —                                        |
| Section    | `{Section} — JusticeCenterID`                       | `Law Enforcement — JusticeCenterID`      |
| Guide      | `{Question} — JusticeCenterID`                      | `What is due process? — JusticeCenterID` |
| Hub        | `{Hub} — JusticeCenterID`                           | `Glossary — JusticeCenterID`             |
| Platform   | `{Page} — JusticeCenterID`                          | `Editorial Policy — JusticeCenterID`     |

Rules: target 50–60 characters before the suffix; the brand appears once, at the end; no
keyword padding; no repeated modifiers ("Guide | Explained | 2026").

### Description templates

The description **is** the entity's `summary` field — the same plain-language sentence the
reader sees at the top of the page. One string, one meaning, no separate "SEO description"
that says something different from the page.

Constraints enforced by validation: non-empty, ≤ 320 characters, no truncation mid-word, no
keyword lists.

### Canonical URLs

Built from the route registry and the canonical host. `metadataBase` is set once in the root
layout. Every page emits exactly one canonical, always the apex `https://justicecenterid.com`
form, never `www`, never with a trailing slash, never with parameters.

Duplicate canonicals across two routes are a test failure.

### Open Graph and Twitter

- `og:type` — `website` for home and hubs, `article` for guides.
- `og:title`, `og:description`, `og:url`, `og:site_name`, `og:locale` (`en`).
- `article:published_time` and `article:modified_time` from the entity's dates on guides.
- `twitter:card` — `summary`.
- **Open Graph imagery does not exist yet.** An earlier draft of this document described a
  build-time generated card; none was ever implemented, and the site shipped
  `summary_large_image` with no image, which degrades to an empty card. The card type is now
  `summary`, which is honest about what is available. When an OG image is added it must
  contain no seal, crest, badge, flag, or emblem, for the same reason the favicon does not,
  and `twitter:card` moves to `summary_large_image` in the same commit — not before it.

### Robots directives

Every route is indexable except `404.html`, which is `noindex, follow`. There is no thin page
needing suppression — that is the intended result of the scaling model, not an omission.

`max-snippet:-1, max-image-preview:large, max-video-preview:-1` are set so that search engines
may show full snippets; on a reference site, a longer snippet is a better answer.

Unpublished entities never reach a URL at all, because the build excludes them.

## 2. robots.txt

Generated by `src/app/robots.ts`:

- `Allow: /` for all agents.
- `Sitemap: https://justicecenterid.com/sitemap.xml`.
- `Host` is not used (non-standard).

No crawler is blocked, including AI crawlers. The content is educational and published to be
read; blocking would contradict the mission. That decision is recorded here so it is a
decision rather than an oversight, and it is revisited if crawl load becomes a hosting
problem.

---

## 3. Sitemap

Generated by `src/app/sitemap.ts` from `src/lib/routes.ts`.

| Field             | Source                                                                                                                                                             |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `url`             | Route registry + canonical host                                                                                                                                    |
| `lastModified`    | The entity's `updatedOn`; for structural pages, the build date is **not** used — a static page whose content did not change does not claim a new modification date |
| `changeFrequency` | Omitted. It is advisory, widely ignored, and inviting a guess is inviting a fabrication                                                                            |
| `priority`        | Set only where it reflects a real hierarchy: home `1.0`, sections `0.8`, guides `0.7`, hubs `0.6`, platform pages `0.3`                                            |

Rules:

- Only `published` entities appear.
- Only routes that exist in the exported output appear — `scripts/verify-output.mjs` asserts
  the sitemap and the `out/` tree agree in both directions, so an empty or failed route cannot
  be advertised.
- No sitemap index is needed at this scale. It is introduced above ~10,000 URLs, split by
  section.

## 4. Structured data

Emitted as JSON-LD by `src/components/seo/JsonLd.tsx`, built by typed helpers in
`src/lib/jsonld.ts`. Every field is derived from real data; no field is populated to satisfy a
validator.

| Page                                                                 | Types                                                                 | Notes                                                                                                                                                                            |
| -------------------------------------------------------------------- | --------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| All pages                                                            | `Organization`, `WebSite`                                             | In the root layout. `Organization` carries name, URL, description, and our own logo. No `address`, `telephone`, `founder`, `foundingDate`, or `sameAs` — we do not invent them.  |
| All pages below root                                                 | `BreadcrumbList`                                                      | Derived from the route registry.                                                                                                                                                 |
| Home                                                                 | `WebPage`                                                             |                                                                                                                                                                                  |
| Section                                                              | `CollectionPage`                                                      | With `hasPart` referencing the section's published guides.                                                                                                                       |
| Guide                                                                | `Article`                                                             | `headline`, `description`, `datePublished`, `dateModified`, `inLanguage`, `isAccessibleForFree: true`, `publisher`, `citation` (from the source records), `about` (the concept). |
| Glossary                                                             | `CollectionPage` containing `DefinedTerm` items in a `DefinedTermSet` | The one place `DefinedTerm` genuinely applies.                                                                                                                                   |
| About                                                                | `AboutPage`                                                           |                                                                                                                                                                                  |
| Contact                                                              | `ContactPage`                                                         |                                                                                                                                                                                  |
| Editorial / Corrections / Methodology / Privacy / Terms / Disclaimer | `WebPage`                                                             |                                                                                                                                                                                  |

### Schema types deliberately not used

| Type                                                                | Why not                                                                                                                               |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `GovernmentOrganization`, `GovernmentService`, `GovernmentBuilding` | We are not a government body. Using these would be a false authority signal, which is the exact failure the positioning forbids.      |
| `LegalService`, `Attorney`, `LegalForceStatus`                      | We provide no legal service.                                                                                                          |
| `NewsArticle`, `ReportageNewsArticle`                               | We are not a news publisher and do not meet news-publisher expectations.                                                              |
| `FAQPage`                                                           | Our pages are explanations, not question-and-answer pairs; marking them as FAQ to chase a rich result would misrepresent the content. |
| `HowTo`                                                             | Actively inappropriate — the site publishes no procedures by policy.                                                                  |
| `Review`, `AggregateRating`, `Rating`                               | We do not rate institutions or countries.                                                                                             |
| `Person`                                                            | No individual bylines exist to describe.                                                                                              |
| `EducationalOrganization`                                           | We are a publisher, not an accredited institution.                                                                                    |

### `citation`

Guides emit their source records as `citation` entries with `name`, `publisher`, and `url`
where public. This is unusual and deliberate: the sourcing is the product, and it should be
machine-readable, not only visible.

## 5. Content freshness

Three visible signals, all from real data:

- **Last updated** — the entity's `updatedOn`.
- **Last reviewed** — the entity's `reviewedOn`, with the review status label
  (`Fact-checked`, `Editorial review`, `Needs update`).
- **Needs-update notice** — a dated notice rendered when `review === 'needs-update'`.

These map to `dateModified` in `Article` structured data. `datePublished` is the entity's
first publication date, recorded once; it is never overwritten by an edit, and it is never
backdated.

We do not put a year in titles, do not re-date a page to look fresh, and do not use a build
timestamp as a modification date.

---

## 6. Internal linking

Internal linking is treated as an IA problem with an SEO benefit, not the reverse.

- Every guide links to its section, at least two sibling guides, and every glossary term it
  defines inline.
- Every hub links to everything it enumerates; every entity links back to the hubs that
  enumerate it.
- Cross-section links exist where the relationship is real; decorative "related" links are
  prohibited, and `related` requires a minimum of two entries precisely so authors have to
  find real ones.
- Link text is descriptive and unique. No "click here", no bare URLs, no "read more" as the
  entire link.
- The footer carries the complete section and hub map, so every page is within two clicks of
  every other.
- **Validated:** every internal link in every content block is checked against the route
  registry by `tests/content/links.test.ts`. A link to a non-existent route fails the suite.

---

## 7. Heading hierarchy

- Exactly one `<h1>` per page, matching the page's primary subject.
- No level skipped. `h2` for sections, `h3` for subsections.
- Headings describe content; they are never used for size, and never contain a call to
  action.
- Playwright asserts heading order on representative pages.

---

## 8. Pagination

None. Hubs are complete lists. When a hub outgrows a single page, the resolution is a narrower
child hub with a meaningful URL, not `?page=2` — a taxonomy problem should be solved with
taxonomy. If pagination ever becomes unavoidable, `rel="next"`/`rel="prev"` alone is
insufficient and the plan is self-canonical paginated URLs plus a full-list view.

---

## 9. Feed

`/feed.xml` — RSS 2.0, generated at build from published entities, newest `updatedOn` first.
It exists so that librarians, educators, and researchers can follow updates without a
platform account, and so that changes to a reference site are observable.

Each item carries title, link, description (the entity summary), `pubDate`, and a stable
`guid` (the canonical URL, `isPermaLink="true"`).

---

## 10. llms.txt

`/llms.txt`, following the emerging convention, generated at build time from the same
registries as the sitemap. It states:

- What the platform is and what it is not (specifically: not a government body, not legal
  advice).
- The editorial and sourcing standards, with links.
- The section and hub map with canonical URLs.
- The published guide list.
- Attribution and reuse expectations.

The reasoning: language models are now a primary route by which people encounter explanations
of institutions. If a model is going to summarise this material, the highest-value thing we can
publish is an accurate, machine-readable statement of what we are — above all, that we are not
official and do not give legal advice. A model repeating that is a correction we do not have to
make later.

---

## 11. Machine-readable editorial information

Beyond `llms.txt`:

- Source records are emitted as `citation` in `Article` structured data.
- Review status and dates are rendered in the page as text, in structured data as
  `dateModified`, and in the DOM with `<time datetime>` so they are parseable.
- `/sources` is a complete, generated index of every source cited anywhere on the site,
  grouped by source type.

## 12. Practices we do not use

| Practice                                            | Why                                                                       |
| --------------------------------------------------- | ------------------------------------------------------------------------- |
| Keyword stuffing, keyword density targets           | Degrades the text for the reader, who is the point.                       |
| Thin programmatic pages (country × topic sweeps)    | Prohibited by the scaling model. A page exists because it was researched. |
| Doorway pages, near-duplicate location pages        | Same reason.                                                              |
| Hidden text, cloaking, link schemes                 | —                                                                         |
| `FAQPage`/`HowTo` markup on content that is neither | Misrepresentation to a search engine is misrepresentation.                |
| Fabricated coverage counts ("200 countries")        | All counts are computed from the registry at build time.                  |
| Year-stamped titles refreshed annually              | Implies a review that did not happen.                                     |
| Auto-generated "related posts"                      | `related` is authored and validated.                                      |
| Buying or exchanging links                          | —                                                                         |

---

## 13. Measurement

No analytics vendor is installed in this phase — no third-party script, no cookie, no
consent banner required, nothing to disclose beyond hosting logs in the privacy policy.

When measurement is added, the constraints are: privacy-preserving, no cookies, no
cross-site identifiers, disclosed in the privacy policy before it ships. Search Console and
Bing Webmaster Tools are the intended first instruments, since they require no client-side
code at all — only DNS or file verification, which is a launch task, not a foundation task.
